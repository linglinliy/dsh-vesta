## 2. 各问题的真实原因（已确认）

### 2.1 M1 选中失败

- 已排除：前台锁（`fgIsTarget=true`）、输入被系统拒绝（`SendInput=1`、菜单可点）、图标点不动（模式确实切换）。
- 已确认：点击原子后**目标邻域像素差为 0**、文本区无新增、无黄色标记——即 **VESTA 没有把该点击当作“选中”**。
- 尚不能确定：是本版本的选中操作序列不同（例如需要按下-保持-释放更长、或需要某个 Preferences 开关），
  还是我们点到的“球”其实是键/边缘。**这是 M1/M2 的唯一阻塞点**，下一轮优先解决。

### 2.2 M4 删除曾失败（已修复）

- 原因：宿主 `rect` 查询偶发返回空 → 可见表判定失败 → 抛“找不到可见的原子列表控件”。**是竞态，不是控件不存在**。
- 修复：`pickVisibleAtomGrid` 增加 4 次重试；`deleteAtomInVesta` 复用已打开的 Edit Data 对话框。
- 修复后结果：2 → 1，稳定通过。

### 2.3 Save As 指定路径失败

- 保存对话框是**新版 Windows DirectUI 对话框**（控件类含 `DirectUIHWND`、`DUIViewWndClassName`）。
- 对其中“可见 Edit”投递 `WM_SETTEXT` 后，实际保存仍用默认文件名/目录 →
  **该控件不接受消息式写入**，需要用 UIA ValuePattern 或“聚焦后键盘输入”。
- 副作用：覆盖了 `D:\calcf\si\POSCAR.vesta`（已实际生成，4172 字节，可查看但请知悉）。

### 2.4 取证静默失效

- 屏幕 **864** 高，而 `captureFullWindow` 默认 **1280×882** → 底部文本区/状态栏落到屏幕外；
- 窗口被移到屏幕外时 `GetWindowRect` 返回 `-32000` 级别坐标，所有截图/点击都在“空白处”执行。
- 规则：动作前必须校验 `IsIconic=false` 且窗口矩形在屏幕内。

## 5. 补充测试（第二轮）

### 5.1 同 PID 新窗口

- `File > New Window`（菜单 101）执行后，按 PID 枚举到的顶层窗口仍只有 **1 个**（`vestaWindows` 返回条目字段与本机不符，hwnd 显示为 undefined，计数需用 `EnumWindows` 复核）；
- 结论：**“同进程多窗口”未复现**，M3 该项需换枚举方法再做；不作为通过项。

### 5.2 遮挡下截图

- 窗口不在前台（被聊天窗口覆盖）时 `PrintWindow(PW_RENDERFULLCONTENT)` 仍成功：1000×700、`ink=0.0994`；
- 结论：**截图通道不依赖前台**，M0 的取证能力可用；但窗口必须在屏幕内（见 2.4）。

### 5.3 导出栅格是“保存对话框”直达

- `File > Export Raster Image...`（104）打开的是标题为 `Export Raster Image` 的**文件保存框**（按钮 `保存(&S)` / `取消` / `帮助(&H)`），不是格式/分辨率对话框；
- 之前看到的 `Export image` 对话框来自另一条路径（Vector/其他），两者不要混用。

### 5.4 文件名输入：消息与字符投递都不生效

在 `Export Raster Image` 保存框中依次尝试：

| 方式 | 结果 |
|---|---|
| 对该框唯一可见 `Edit` 投递 `WM_SETTEXT` | 无效（保存仍用默认名） |
| `clickat` 聚焦 + `chars` 投递完整路径 + `Enter` | 无效（对话框不关闭、无文件产生） |

**真实原因**：这是 Windows **DirectUI** 文件对话框（控件类 `DirectUIHWND`/`DUIViewWndClassName`），
其文件名框不接受 `WM_SETTEXT`/`WM_CHAR` 这类投递消息；需要 UIA `ValuePattern` 或真实键盘输入（SendInput）才能改路径。

## 7. 第四轮：输入注入的**真实原因**与突破

### 7.1 根因一：`INPUT` 结构体尺寸必须是 **40 字节**

- 之前自写的 C# 结构体实际尺寸 **48 字节**（`type(4)+KEYBDINPUT(24)+3×int(12)`，再加对齐）；
- 结果：`SendInput` 返回 **0**、`GetLastError=87`（`ERROR_INVALID_PARAMETER`）；
- 修正为 `[StructLayout(LayoutKind.Sequential, Size = 40)]` 后：`SendInput=1`、`err=0`，
  实测 Unicode 键入成功：`typed=33/33`、`typed=30/30`。

**结论：键盘注入本身完全可用。** 此前“DirectUI 文件框不接受输入”“键盘被策略拦截”的判断
全部作废——真正原因是结构体尺寸写错，系统直接拒绝。

### 7.2 根因二：`SendMessage(WM_COMMAND)` 打开模态对话框会**阻塞调用线程**

- 用 `SendMessage` 触发 `File > Save As` 时，PowerShell 线程阻塞在调用里，直到对话框关闭；
- 改用 `PostMessage` 后立即返回、对话框正常弹出。

**规则：凡是会弹窗的命令一律用 `PostMessage`。**

### 7.3 突破：Save As 端到端成功

流程（可复现）：

1. `PostMessage` 主窗口 `WM_COMMAND(5004)`；
2. 按标题 `Save As` 找到对话框，取其中唯一 `Edit`；
3. 真实点击该 Edit 聚焦 → `Ctrl+A`；
4. 用 `SendInput` + `KEYEVENTF_UNICODE` 键入完整路径；
5. `Enter` 提交。

**证据**：生成 `D:\calcf\m-report\uia-final.vesta`（4172 字节），内容含
`#VESTA_FORMAT_VERSION 3.5.4`、`CRYSTAL`、`CELLP`、`STRUC`——是**有效的 .vesta 工程文件**。

### 7.4 导出栅格的**真实顺序**（已查明）

`File > Export Raster Image...`（104）不是一步保存，而是三步：

```
Export Graphics（格式/分辨率） → OK → Save As（填路径）→ 保存 → Export image（透明背景）→ OK
```

注意：本轮生成的 `exported.png` 实际是 **TIFF 内容**（文件头 `4D4D002A`），
说明**格式由 Export Graphics 决定，改扩展名不会改格式**。

### 7.5 对前文结论的更正

| 前文结论 | 更正 |
|---|---|
| 2.3 DirectUI 文件名框不接受 `WM_SETTEXT` | 真因是 SendInput 结构体 48≠40；改用真实键盘输入后**可用** |
| 5.4 `WM_CHAR` 也不生效 | 同上；`WM_CHAR` 对 DirectUI 仍不可靠，但 SendInput 可 |
| 5.3 导出栅格是保存对话框直达 | 实际顺序：**Export Graphics → Save As → Export image** |

### 7.7 导出 PNG 的补充发现（本轮收尾）

- `Export Raster Image` 的保存对话框里带**文件类型下拉框**（`ComboBox`），默认是 **TIFF**；
  这就是为什么把文件名写成 `.png` 仍然得到 TIFF 内容（头 `4D4D002A`）。
- 想导出真正的 PNG，必须在该下拉框里选中 `PNG`（`CB_FINDSTRINGEXACT` + `CB_SETCURSEL` + `CBN_SELCHANGE`），
  再填路径保存；本轮已定位到该控件，但**端到端尚未跑通**（窗口句柄在多轮对话框后发生变化，命令发到了旧句柄）。
- 教训：VESTA 主窗口句柄在多次弹窗/另存后可能变化，**每次动作前必须重新枚举主窗口**，不能缓存。

### 8.3 修复过程中**新遇到的问题**（真实原因）

1. **`wininfo` 首次实现失效，归属校验被静默跳过**
   - 现象：删除日志显示 `pid=?`，但流程继续执行；
   - 原因 1：宿主 C# 里**没有 `GetWindow` 声明**，`wininfo` 抛异常；
   - 原因 2：PowerShell 无法把 `out uint` 绑定到 `$pidv = 0`（int32）；
   - 修复：新增 `PidOf(IntPtr)` 助手与 `GetWindow` 声明；并把归属校验改为“拿不到就抛错”，避免“校验形同虚设”。

2. **脚本化替换导致花括号重复，core.js 语法错误**
   - 现象：替换函数体后 `node --check` 报 `Unexpected token '}'`；
   - 原因：切片边界 `end + 1` 遗留了原函数的结尾 `}`；

### 8.6 修复过程中又发现并修掉的环境问题

**MCP 一致性测试误报红**（`test/mcp-parity.test.mjs` 3 项全挂）：

- 现象：`AssertionError: MCP 服务器没有输出；stderr：`（stderr 为空）；
- 原因：测试用 `spawnSync('node', …)` **按名字找 node**，依赖 PATH；
  本机 PATH 里没有 node（只能 `C:\Program Files\nodejs\node.exe`），spawn 直接 ENOENT；
- 这**不是代码回归**，而是环境差异：在 PATH 含 node 的机器上不会出现；
- 修复：测试改用 `process.execPath`（当前 node 可执行文件的绝对路径），两处 spawn 全部替换；
- 修复后：`mcp-parity` **3/3 通过**，回归套件 **28/28**，selfcheck **74/74**。

**教训**：测试里不要按名字 spawn 解释器，一律用 `process.execPath`；否则在精简 PATH 的环境里会误报。
