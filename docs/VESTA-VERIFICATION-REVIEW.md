本轮独立确认：

- `D:/calcf/verify/export-png2.json` 最后一行却记录 `file=True size=2012255 head=4D-4D-00-2A...`，与当前 PNG 文件不同。不能将该日志作为当前 PNG 的一一对应成功证据。可能来自不同轮次，需由新 runId 清单绑定；本次不推断具体原因。
- PC2 对应 `pc-menu-after.png` 实际显示 DSH 聊天界面，未显示 VESTA 菜单；73.55% 差异不能证明真实输入已到达 VESTA。

## 2. 必须优先修正的试验问题

### R1：PC2 是无效正对照（P0）

证据路径：`D:/calcf/verify/2026-10-28T13-05-24/pc-menu-after.png`。该图为其他应用画面，不是 VESTA 菜单，说明至少该时刻的屏幕捕获区域被其他窗口覆盖或捕获了错误内容。试验用 CopyFromScreen，不会自动保证采集的是目标窗口。

处理：撤回“PC2 证明真实输入可达 VESTA”的结论。正对照必须在全窗口证据里显示 VESTA 主窗口及其实际打开的 File 菜单，记录前台与命中窗口归属；若是屏幕捕获，还要确认当前区域没有被其他窗口遮挡。捕获后验证内容，失败就停止该轮。菜单打开成功与画布像素大幅变化没有必然对应关系。

### R2：命中画布不等于命中球，当前检查甚至只判断了根窗口（P0）

`VT.Hit` 通过 `GetAncestor(hit, 2) == root` 设置 inside，表示命中同一根窗口，不代表点在球面内部。现有日志 hit 恰为画布句柄，仍只能证明窗口归属，不能排除球的位置或选择模式错误。

处理：为每个试次保存原始截图、画布边界及目标标注图，记录坐标变换与实际鼠标位置，确认目标点确在一个无遮挡球面内部。模式切换后如画面变化必须重新定位。蓝色像素聚类可能包含键、边缘或多个球，不能只用最大聚类质心证明球心；先人工检查一个目标点即可，不必立即重写复杂识别算法。

### R3：“8 个模式”没有被证明（P0）

脚本以竖直工具条总高度除以 8 得 pitch，再平均点击 8 个位置。工具条的空白区域、内边距和按钮间隔不必均分总高度，因此这不等于实际点击八个图标，更不等于激活八种语义模式。与先前按截图估计图标间距的方式也不一致。

处理：停止按 toolbarHeight/8 计算按钮中心。先依据截图、tooltip 或可访问状态准确识别 Select 一个入口并记录其点击反馈；对按钮框和目标点叠加标注。矩阵中把 iconIndex 改为候选点击位置，只有确认语义后才标 Select 等模式名称。报告“32 次候选点击无观测到变化”，不报告“8 模式均失败”。

### R4：E1 解析失败被悄悄吞掉（P1，已独立复现）

当前代码先用 `l.trim().startsWith('{')` 过滤，随后却 `JSON.parse(l)`，没有把 trim 后的内容传入解析；Windows PowerShell 写出的 UTF-8 BOM 导致第一条 E1 失败。清单中 geometry 为 null，却仍将 E1 写为通过。

处理：输入层统一去除文件开头 BOM，采用标准 JSON 数组或明确命名为 `.jsonl` 的逐行格式，逐条解析并校验 schema；E1 缺失或任一关键记录损坏则返回基础设施失败，禁止继续给出几何通过结论。使用现有文件添加一个无 GUI 的解析回归测试，并测试 BOM/无 BOM、CRLF、空行和非法记录。

### R5：旧试次候选会触发当前选择的 Delete（P0）

Node 汇总任意 E2 试次的局部差异或黄色像素超过阈值就设 selectionObserved=true，然后在全部试次结束后对当前窗口发 Delete。早先试次的“候选选择”与循环结束时的选择集合没有绑定；旋转、其他变化或错误截图也可能触发阈值。

处理：差异仅作为候选，不可直接驱动隐藏。先明确一个成功选择试次，在同一场景版本下重放并即时核验目标及唯一选择，再执行隐藏；每步观测确认。移除自动扫描结束就发 Delete 的逻辑。截图差异检测器未校准前，仅产出诊断，不执行后续动作。

E4 只比较结构行数和日志里的 rendered 计数也不足：日志中“28 atoms”不保证是当前可见数。采用目标局部画面、实际当前结构与受控恢复三项证据；恢复前提是测试副本无既有隐藏对象。Esc 不能作为对用户现场的无副作用通用清理。

### R6：试验没有隔离和完整失败信号（P1）

当前 `running[0]`、全局 `listControls('main')` 可能与所选 PID 不一致；已有实例不验证文档就使用，试验会移动窗口、切模式、缩放，因此注释“只读验证”不准确。入口存在硬编码 core 的绝对路径，且 result=failed 时最终仍 process.exit(0)。宿主清理也未在顶层 finally 里保证。

处理：要求显式测试窗口/结构标识，校验 PID、主窗口、画布与文件一致；专用临时副本运行，预检不匹配则停止。使用相对模块导入，给出可配置夹具和输出目录。区分失败/阻塞/跳过及退出码；关键异常要写清单并清理宿主及本轮按键状态。绝不能将未能创建试次而得到的 0 条记录解释成选择能力失败。

当前 PowerShell 最后只追加一条 `phase=E3` 的 note，未实际发送后台点击；manifest 称 E3 阻塞。应删除假动作标记或将其明确命名 planned/skipped，保证日志与清单一致。

## 3. PNG 导出：产物通过，流程需继续完善

接受新 PNG 的实际文件、解码与尺寸证据；不据此认定当前脚本是已验证的通用状态机。

源码仍有以下局限：

- `Find` 通过全局标题包含关系选择窗口，缺少 PID/owner 绑定；首个 ComboBox/Edit 不保证是文件类型/文件名控件。
- 使用 Home + Down×4 硬编码格式位置，不核实当前选项文本；`cur=4` 不自带 PNG 语义。
- 开头在尚未绑定目标前发 Esc，可能作用于其他前台应用；不应这样清理。
- 后续对话框循环最多三次按 Enter，依赖默认按钮，不能作为可恢复状态机；未知覆盖确认不应被无条件接受。
- 只验证 Test-Path/长度/头，不能证明文件由本轮创建；SendInput 返回值在部分按键函数未检查。输出目录预检、取消、错误与清理未完整处理。

下一步：每次使用唯一且不存在的目标路径，在绑定会话后枚举所属对话框，用控件语义和实际选项文本设置 PNG，按识别状态推进。未知状态停止并保留截图。最终记录同 runId 的输入参数、格式文本、输出修改时间、长度、SHA-256、解码尺寸和最终截图。保存工程需另开副本重新加载，核对结构及需要保留的样式，不只检查格式关键字。
